# Глобальные правила pi-сессий

Этот файл — глобальный контекст pi: `~/.pi/agent/AGENTS.md` (симлинк на
`modules/home/pi/AGENTS.md` в `~/.nix`). pi подхватывает его всегда, в
любом каталоге, плюс `AGENTS.md`/`CLAUDE.md` по цепочке каталогов от cwd
до `/` (`dist/core/resource-loader.js`, `loadProjectContextFiles`).
Правила конкретного репозитория — в его собственном `AGENTS.md`.

## Всегда работать в git worktree

Не править файлы в основном (главном) чекауте репозитория. Перед первой
правкой заводить worktree под задачу:

```bash
git -C <repo> worktree add <repo>/.pi/worktrees/<имя> -b pi-<имя>
```

Все правки, коммиты и сборки — внутри этого worktree, по абсолютным
путям. В основной чекаут трогать нечего, кроме интеграции:

```bash
git -C <repo> merge --ff-only pi-<имя>
git -C <repo> push
git -C <repo> worktree remove <repo>/.pi/worktrees/<имя>
```

Зачем: основной чекаут — это рабочая версия (для NixOS-конфига — та
конфигурация, которая реально переключена, с gitignored секретами и
локальными файлами); параллельные сессии (pi и Claude) не затирают друг
друга; незавершённая правка не оставляет основной чекаут в грязном
состоянии; ветку можно отбросить целиком.

Гранулярность — один worktree на задачу, не на сессию. Задачу закончил —
worktree удалил (`git worktree remove`, не `rm -rf`), ветку до слияния не
трогать.

### Когда worktree не нужен

- Только чтение: чтение файлов, поиск, `git log`/`git show`, диагностика,
  `nix path-info`, `journalctl` — всё это и так не меняет рабочее дерево.
- Одна разовая команда без правок (собрать, проверить, запустить).
- Репозиторий без ветки-приёмника (detached HEAD, временная копия) —
  сказать пользователю, что правилу нечего применить, и работать как есть.

### Грабли, о которых помнить

- **Gitignored-файлы в worktree отсутствуют.** Секреты, `.env`, локальные
  конфиги, `ssh/`, `xray/` — их там нет. Прежде чем уходить в worktree,
  проверить, не нужны ли они для сборки/оценки; если нужны — либо
  скопировать, либо остаться в основном чекауте и сказать пользователю.
- **Flakes видят только git-tracked файлы** — новый файл в worktree надо
  `git add`, иначе флейк его не увидит (в основном чекауте та же история).
- **Не переписывать уже запушенное**: `merge --ff-only`, а не rebase
  общего `master`; force-push не использовать.
- Если в основном чекауте в этот момент чужие незакоммиченные правки —
  не трогать их и не «чинить»; интеграцию делать, только если она не
  конфликтует, иначе попросить пользователя.

## Коммиты подписывать собой (pi), не пользователем

Гит-идентичность по умолчанию в этом окружении — человек (`vec137
<you@example.com>` из `programs.git` в `~/.nix`), поэтому коммит агента без
явного указания личности пишется на пользователя. Свой коммит всегда подписывать
собой — по образцу claude-коммитов в `~/.nix` (у них автор и коммиттер — сам
агент, `Claude <noreply@anthropic.com>`; у pi в этом же репозитории исторически
`pi <pi@noreply.local>`, так что подпись уже устоялась). Правило для любого
репозитория, не только `~/.nix`:

```bash
git -c user.name=pi -c user.email=pi@noreply.local \
    commit --author="pi <pi@noreply.local>" -F <файл-сообщения>
```

`-c` задаёт и автора, и коммиттера (committer берётся из `user.*`), но `--author`
всё равно нужен: если в окружении стоят `GIT_AUTHOR_*`, один `-c` автора не
перебивает. Проверить после коммита:

```bash
git log -1 --format='%h | %an <%ae> | %cn <%ce>'   # обе колонки — pi
```

Если коммит уже запушен с чужой подписью — переподписать можно только так:
`git -c user.name=pi -c user.email=pi@noreply.local commit --amend --no-edit
--author="pi <pi@noreply.local>"` и `git push --force-with-lease=master:<старый
sha>`. Это исключение из пункта про запушенное выше, и делать его надо, только
если пользователь прямо об этом попросил (в `~/.nix` прецедент есть — репозиторий
с одним потребителем).
